# KernelLedger: notebook versioning and resumable sessions

Build a notebook system that versions source cleanly, records what actually executed, and restores saved work. Keep the notebook interface familiar while storing source, execution events, outputs, and checkpoints separately.

This is a proposed implementation plan, not an implemented system. KernelLedger is a new project. Start with Python/IPython and JupyterLab; support ordinary variable checkpoints on Windows, then explore full process snapshots in a controlled Linux environment.

## 1. Define the guarantees

Offer distinct operations with explicit meanings:

| Operation | Guarantee |
| --- | --- |
| Open source | Recover code, Markdown, cell IDs, ordering, and intentional notebook metadata. |
| Inspect a run | Show recorded executions and their outputs without executing code. |
| Replay a run | Execute recorded source in recorded order in a fresh kernel; report environmental differences. This does not guarantee identical results. |
| Restore a variable checkpoint | Restore supported user objects from a saved object graph in a compatible environment. Report unsupported or missing resources. |
| Resume a process snapshot | Resume a supported process under a validated host configuration. This is an optional platform-specific capability. |

History is not live memory, and a Python object checkpoint is not an entire process snapshot. Neither operation restores a remote service or undoes external side effects.

## 2. Establish separate storage layers

Use stable notebook and cell IDs. Associate outputs with executions, because the same cell and identical source can produce different results under different kernel state.

Proposed layout:

```text
analysis/
  notebook.json                  # Notebook ID, ordered cell IDs, essential metadata
  cells/
    <cell-id>.py                 # Code source
    <cell-id>.md                 # Markdown source
  checkpoints/
    <checkpoint-id>.json         # Selected published checkpoint descriptors

.notebook-state/                 # Local runtime storage; ignored by Git
  sessions/<session-id>/
    events.jsonl                 # Human-readable execution/event export
    environment.json
  blobs/<content-hash>           # Source snapshots, outputs, checkpoint payloads
  index.sqlite                  # Transactional event store and local index
```

Use SQLite as the local transactional store and export immutable JSONL session records for sharing and review. Do not maintain two independent writable histories. Keep large blobs outside Git, with local filesystem storage first and a remote artifact backend later.

For an early prototype, use Jupytext paired `.py`/`.md` and `.ipynb` files instead of immediately introducing a custom source format. Commit the text source and retain outputs locally. Select the custom layout only after testing import/export fidelity and merge behavior. Preserve intentional metadata and Markdown attachments; classify execution counters, transient editor state, and generated outputs as runtime data.

Git tracks source and optional selected run/checkpoint descriptors. It does not need to interpret live kernel state. Concurrent sessions get separate histories rather than one shared timeline that must be merged.

## 3. Make source diffs and merges useful

Preserve cell IDs through editing, reordering, import, and export. Duplicate or missing IDs must be repaired explicitly. Code edits should change code text; moving cells should primarily change the ordering manifest in the custom layout.

Implement `.ipynb` import and export so notebooks remain usable by existing Jupyter tools. An exported notebook is a materialized view of source plus explicitly selected execution outputs. Preserve the source revision associated with those outputs, and label mismatches when outputs are shown beside edited code.

Git can merge independent text edits. Conflicting cell order changes, concurrent edits to one cell, and cell deletion versus editing still need resolution. Add a cell-aware merge interface only if ordinary text merging proves insufficient.

## 4. Record execution at the time it happens

Use a JupyterLab extension to supply notebook ID, cell ID, and source revision. Use a recording layer at the kernel/server boundary to persist execution requests, replies, and IOPub events. Python kernel hooks can supplement this with namespace/checkpoint operations, but must not be the only source of rich output capture.

For each execution, record:

- Session ID, kernel instance ID, request/message ID, and local ordering information.
- Notebook/cell attribution when available; record console or unattributed requests honestly.
- Exact submitted source or an immutable reference to it, regardless of later edits.
- Execution count where available, request options, request/start/end times, and completion status.
- Output event references and success, error, interrupted, aborted, or incomplete status.
- Links to source revisions and checkpoints when applicable.

Persist requests before execution where possible, then append lifecycle and output events. Use request IDs for correlation rather than only execution counts. A restart creates a new session and records its parent/restored checkpoint when applicable.

Retain stdout, stderr, display data, execution results, and errors. Handle `clear_output`, display updates, and asynchronous outputs as events, then derive the visible output state. Preserve historical events even if the visible output is cleared. Outputs with missing attribution must remain explicitly unattributed.

Record the observed order, not a claim of universal causal order across threads, clients, or concurrent subshells. The initial supported mode is one sequential kernel execution stream. Silent/internal executions need an explicit policy so maintenance commands do not pollute the user's timeline and relevant unrecorded activity is disclosed.

Use IPython's existing persistent history for best-effort recovery of earlier inputs. It cannot reconstruct missing historical plots, timestamps, cell attribution, or past variable values.

## 5. Add history inspection and controlled replay

Provide a timeline that shows repeated runs and exact historical source. Let users inspect outputs, compare executions, export a session, and open the source revision that produced a result.

Replay into a fresh kernel using the recorded source sequence, including edited or deleted cell versions. Capture Python/package versions, interpreter/platform details, working directory, selected non-secret configuration, input data references/hashes, and relevant random-generator states when supported. Dependency metadata does not bundle the packages or external datasets themselves; define how those dependencies are retrieved.

Replay is an explicit action because it can repeat writes, network requests, and other side effects. Do not automatically replay failed cells or reconnect to external systems during inspection. Report drift, missing inputs, and non-reproducible results rather than promising deterministic execution.

## 6. Save user variables as a consistent checkpoint

Checkpoint between cell executions. Pause cooperative background work where supported. If background mutations cannot be controlled, report that a fully consistent checkpoint is unavailable rather than silently claiming consistency.

Inspect the user namespace and exclude kernel internals and transient recorder objects. Serialize supported user objects together as one graph so shared references, aliases, and cycles can be preserved. Evaluate dill as the first Python serializer; add specialized serializers only where needed for supported data/model types.

Run preflight checks and expose unsupported objects before publishing a checkpoint. Save a manifest describing included/excluded objects, serializer and dependency versions, payload hashes, the execution boundary, source revision, environment, and restore requirements. A partial checkpoint must be labeled partial. Never silently skip a variable and call the checkpoint complete.

Checkpoint writing must be atomic: write temporary payloads, verify and flush them, then publish the manifest. A crash must leave either a valid checkpoint or an identifiable incomplete artifact.

Restore into a fresh compatible kernel. Validate dependencies and payload hashes, restore the user object graph, then run explicitly configured resource reconstruction hooks. Identify files, connections, threads, generators, tasks, and native/device resources that require reconstruction or cannot be restored. Python functions and classes can often be serialized, but arbitrary live runtime resources cannot be assumed to work.

Store history and outputs with the checkpoint through immutable references so it presents as one saveable bundle. For offline sharing, export a self-contained archive including all referenced blobs; list dependencies that still remain external.

Checkpoint blobs are executable deserialization inputs. Only restore trusted artifacts, and avoid including credentials in environment captures or shared snapshots. Local snapshots may contain sensitive values that are already present in user variables.

## 7. Integrate notebook save and restore controls

Provide clear actions:

- Save source.
- Inspect execution history.
- Save checkpoint, showing any unsupported resources.
- Restore checkpoint in a new kernel.
- Replay a selected session.
- Export/import a notebook or session bundle.

Show whether visible outputs match the current source and identify the session/checkpoint behind them. Editing source should not erase historical results. Kernel restart should preserve saved history and checkpoints.

Start with manual checkpoints. Add autosave at configured successful execution boundaries only after measuring checkpoint time, size, and consistency. Saving source remains lightweight; large state saves should have progress and cancellation.

## 8. Explore full process snapshots separately

Prototype CRIU with a disposable Linux kernel process or supported container configuration. Validate notebook reconnection as well as process restoration: the saved process may carry old connection files, ports, paths, credentials, and socket state.

Test memory, threads, file descriptors, supported connections, subprocesses, and resumption position under a controlled environment. Define filesystem handling explicitly; restoring process memory alone does not restore modified files. Record host/kernel/library constraints and test supported GPU checkpoint plugins only as a separate capability.

Native Windows is outside the CRIU path. Evaluate a managed Linux environment or VM snapshot if exact resumption is required. Neither approach guarantees that a remote database, expired credential, or changed external service resumes as before.

Keep process images outside ordinary Git. Expose this mode only for configurations with demonstrated restore reliability; do not make it a prerequisite for clean notebook versioning.

## 9. Deliver in phases

| Phase | Deliverable | Completion evidence |
| --- | --- | --- |
| 1: Source separation | Jupytext prototype, Git rules, notebook import/export | Running a cell does not change tracked source; Markdown and intentional metadata survive round trips. |
| 2: Durable history | Session recorder, exact source snapshots, output storage, timeline export | Repeated/out-of-order runs remain inspectable after edits, restarts, and recorder crashes; rich output updates render correctly. |
| 3: Variable checkpoints | Object graph save/restore, compatibility manifest, atomic publishing | Restore supported variables in a fresh kernel, preserve aliases/cycles, and identify unsupported resources. |
| 4: Integrated workflow | Notebook controls, replay, bundles, source-aware output display | A user can save, close, reopen, inspect, and continue a supported session without rerunning earlier cells. |
| 5: Collaboration and storage | Published descriptors, artifact backend, retention, optional cell-aware merge | Teammates can fetch selected checkpoints and independently merge source; missing artifacts are reported clearly. |
| 6: Full process experiment | Linux snapshot/resume proof of concept | A documented supported environment restores a kernel and reconnects its notebook frontend. |

Do not assign dates until the target editor, deployment environment, and prototype results are known. Begin with JupyterLab and local Windows storage, and validate the key restore limitations before building broad integration.

## 10. Validate the behavior that matters

Use representative notebooks with code, Markdown/attachments, NumPy arrays, DataFrames, custom objects, shared references, errors, rich displays, random state, and unsupported resources.

Check meaningful scenarios:

- A run changes outputs but leaves tracked source unchanged.
- Editing/deleting/reordering cells preserves attribution to historical source.
- Two executions of identical source can retain different outputs.
- Two clients or sessions do not overwrite or falsely merge histories.
- A restart retains durable records; an interrupted write does not publish a corrupt checkpoint.
- Restoring a supported checkpoint works in a fresh kernel and preserves object relationships.
- Dependency drift, missing blobs, partial saves, and unsupported resources produce useful reports.
- Replay uses historical source, and inspection performs no execution.
- Bundle export contains every required stored artifact, with external dependencies listed.
- Retention removes only unreferenced blobs and protects selected checkpoints.

Measure save/restore latency, storage growth, and notebook responsiveness on representative sizes before choosing autosave intervals or optimization strategies. Account for mutated objects when considering incremental checkpoints; a reused variable name or cell hash is not enough to identify unchanged state.
